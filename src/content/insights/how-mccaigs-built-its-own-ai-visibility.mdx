mccaigs built its own AI Visibility system the same way it would advise a client to approach the work: start with approved facts, make the website clearer, and connect the public signals.

The goal was not to guarantee inclusion in AI answers. It was to make the business easier for visitors, crawlers, and answer engines to understand.

## The public page system

The first step was creating a connected set of static pages around [Answer Engine Optimisation](/answer-engine-optimisation), [AEO Scotland](/answer-engine-optimisation-scotland), [AEO UK](/answer-engine-optimisation-uk), [AI Search Optimisation](/ai-search-optimisation), [AI Visibility](/ai-visibility), [ChatGPT SEO](/chatgpt-seo), [Google AI Overviews readiness](/google-ai-overviews), [llms.txt](/llms-txt), and [AI-ready websites](/ai-ready-websites).

Each page answers a specific question, links to related pages, and keeps the promise boundary clear.

## The AI-readable layer

mccaigs also added llms.txt, llms-full.txt, and public assistant knowledge files in JSON and Markdown. These files give answer engines a safe, approved source for describing the business.

They do not replace the website. They support it.

## The assistant layer

The [deterministic Assistant](/assistant) uses approved static knowledge. It now understands AEO, AI Visibility, AI Search Optimisation, ChatGPT SEO, Google AI Overviews, Gemini, Claude, Perplexity, llms files, AEO Audit, AEO Implementation, and AI Visibility Management.

When the assistant does not know, it should say so rather than inventing an answer.

## The measurement layer

An AI Visibility Report looks at signals such as entity clarity, structured data coverage, FAQ coverage, crawlability, llms.txt presence, and prompt checks across tools such as ChatGPT, Gemini, and Google AI.

That report is evidence for improvement. It is not a guarantee of rankings, inclusion, or recommendations.
